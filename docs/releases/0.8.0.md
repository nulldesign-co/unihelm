# Unihelm 0.8.0

The release workflow writes the install and verification sections of a release's
notes. This file is the other half — what changed and what an operator has to do
about it — kept in the repository so it is reviewed like anything else and does
not exist only inside a GitHub draft.

0.8.0 closes 85 defects reported from a walkthrough of a fresh install on a new
server, 23 more found by a pre-release review of those fixes, and replaces how
the panel sends mail.

---

## Do this after upgrading

### 1. Move mail onto the local MTA

```bash
unihelm mail mta install
```

Until you run it, mail keeps working exactly as it did — the old per-site
configuration is left in place and is only removed once the new path is
verified. After you run it, mail works from **every** language on the machine
rather than only from PHP, and the relay credential stops being readable by your
tenants.

`unihelm mail mta status` says where a machine is, including whether any per-site
files are left over.

### 2. Expect the panel's direct port to close

If you attach a domain and certificate to the panel (`unihelm cert panel`), the
panel now narrows itself to loopback and closes the firewall hole it opened for
its own port, once it has confirmed the vhost is serving. **Your browser will
lose the connection and the panel comes back at `https://<your domain>/`.**

The operation says so before it restarts. To undo it, set `panel.listen` back in
`/etc/unihelm/config.toml` and restart `unihelm-web`.

### 3. Check reseller accounts if you use them

`dns_manage` is no longer a default reseller permission. It granted nothing at
all before this release, so nothing they could do stops working — but the
permission list on those accounts will look different. See "The reseller
boundary" below for why.

## What was wrong, and is not now

### Mail was a PHP feature, and every tenant held the relay credential

Mail was delivered by giving each site its own `msmtp`, named in that site's
PHP-FPM pool. Two things followed from that, and neither was visible:

- **Every tenant could read the credential the server itself sends with.** msmtp
  runs as the site's own Linux user, so the file holding the relay username and
  password had to be readable by that user. One relay, one credential, copied
  into every site's file. A customer reading their own copy could send mail as
  the operator — a blacklisting that takes every other customer's mail with it.
- **Nothing but PHP could send at all.** A Node application had no mail path. A
  containerised application had none. A server with no PHP installed — an
  ordinary configuration for a panel that installs databases as containers — had
  no mail whatsoever. Meanwhile `cron` had been writing `MAILTO=` into every
  tenant crontab since the feature shipped, for a mail system that did not
  exist: every failing scheduled job's output went nowhere.

A Postfix null client replaces it. Postfix reads the credential as root before
dropping privileges, so it is `0600` and no tenant can open it. Mail is now a
property of the machine: `mail()` through `/usr/sbin/sendmail`, everything else
through `127.0.0.1:25`, cron through its own `MAILTO=`.

### The firewall locked operators out of the panel that switched it on

`fw.enable` opened SSH and nothing else, so a fresh install that turned the
firewall on from the Firewall page shut the door it was turned on through. It
looked like it had worked, because netfilter keeps established connections — the
lockout appeared on the next page load or from a second device.

### The panel assumed nginx on machines that had never had it

`webserver::active` answered nginx whenever its setting was absent, and that
setting is written in exactly one place: the end of a successful switch. A server
where somebody installed Apache from the Stack page and never switched — because
there was nothing to switch *from* — had the panel convinced otherwise: a
"Serving" badge on an nginx that was not installed, and `site.create` writing
nginx vhosts into a directory httpd never reads, reporting success.

It probes the machine now, and a probe that cannot tell says so instead of
writing down a guess.

### No PHP version could be installed

apt does not sniff a keyring named in `Signed-By:` — it reads `.asc` as
ASCII-armoured and `.gpg` as binary — and Surý publishes binary OpenPGP while the
panel hardcoded `.asc`. The repository was unsigned as far as apt was concerned,
on every machine, from the first release that had it.

### The containerised engines were connected to nothing

0.3.0 moved every database and cache into a container — built, started,
health-checked, sealed with a generated root password, recorded in a registry —
and then nothing used any of it. The Stack page reported a running MariaDB as
"Not installed", and `db.create` failed on what had become the default install
path, because the database module only ever built a socket client and there was
no socket.

### Anyone could lock an administrator out, from anywhere, permanently

The login throttle counted failures by username alone, with no address
dimension. Five wrong passwords for `admin` every fifteen minutes — from
anywhere, unauthenticated — kept the real administrator out with the correct
password from their own address. Refused attempts were also never recorded, so
Sentinel went blind exactly when an attack got serious.

### The reseller boundary

The pre-release review found that `dns_manage` gated no operation before this
release, and that the five DNS operations added in it attached to that
permission — which resellers hold by default — with no tenant scoping at all. A
reseller could have enumerated the operator's entire Cloudflare account and
deleted or repointed any record in it.

It was caught before release and never shipped. The operations refuse a
non-global scope, and the permission is no longer a reseller default.
`process.list` and `server.reboot.status` had the same shape — one returned every
tenant's command lines, the other every domain on the machine — and got the same
treatment.

### Sundry, each of which cost somebody an afternoon

Every static file was served with none of the security headers, because nginx
drops the inherited list in a location that sets a header of its own. FPM pool
files and Node unit files were world-readable, and the units hold every
`Environment=` line. `php_ini_overrides` was rendered after the `open_basedir`
and `disable_functions` guards, where the last assignment wins. A database named
`order` was a syntax error. Containers published their ports to the internet
past the firewall, because Docker's DNAT rule runs before ufw's INPUT chain.
Adminer ran as the account that owns `panel.db`. Redis, Valkey and Memcached ran
with no authentication, and on a shared host "localhost only" is not a boundary.

## What is new

- **WordPress** has a page. The backend was complete, registered, routed,
  documented and reachable only from a command line.
- **Git deploys.** Attach a repository to a site and pull it.
- **Applications** take a build command and a start command instead of being
  pinned to a single entry file.
- **Docker** can remove, pull and prune images, and manage volumes; there is a
  small curated template catalogue.
- **DNS** can manage Cloudflare zones and records.
- **Processes** are visible, with a kill that refuses the panel's own units, pid
  1 and system uids by name.
- **Panel accounts** can be managed from the web, and a password can be changed
  without a shell.
- **Reboot-required** is detected and shown, with a restart that names every site
  that stops.
- Alert rules can be **deleted**. Sites take **aliases**, and a site whose
  creation failed can be **finished** rather than recreated. The file manager has
  **Move**, folder upload, and a permissions grid instead of an octal box.

## Known limitations

**A Docker network created after the MTA was configured is not in
`mynetworks`**, so containers on it get `Relay access denied` until
`unihelm mail mta install` is run again. The MTA reads Docker's networks when it
is configured, and `unihelm mail mta status` reports when that view has gone
stale rather than leaving it to be discovered.

**A container on a `macvlan`, `ipvlan` or `overlay` network cannot send mail
at all.** Those do not reach the host through a bridge gateway, and nothing in
this release makes them able to. They are named in `mail.mta.status` rather than
silently omitted.

**The WAF cannot run on Ubuntu 22.04 or EL 10.** There is no ModSecurity
connector package for nginx on either, and the panel now says so by name instead
of naming a package that does not exist. On the releases where one does exist, it
is built against that distribution's nginx and will not load beside nginx.org's.

**Memcached runs without authentication.** It has only SASL, which needs a build
that supports it. Redis and Valkey get generated passwords; Memcached does not,
and the recipe says so rather than implying otherwise.

**Containers created before this release keep their old settings.** A cache that
was created without a password still has none until it is recreated.

## For anyone reading the source

Four of these defects were the same shape: a correct, tested, documented piece of
work that nothing called. A repository resolver, a `runtime` field the page was
already sending, three site operations, a pair of reboot operations, two route
modules never declared as modules, a CLI secret nothing filled, and
`engine::root_connection`, whose doc comment named a caller it did not have.

Every one of them had passing tests, because the tests tested the piece and
nothing tested the wire. They were caught by the CI gates and by clippy's
dead-code warning. `docs/design/engines-are-not-connected.md` writes up the
pattern; the short version is that **a function whose doc comment describes its
caller, and has none, is a bug**.
