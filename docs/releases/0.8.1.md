# Unihelm 0.8.1

A correction to 0.8.0, released the same day. **There is nothing to run after
upgrading** — which is the whole point of it.

## What 0.8.0 got wrong

Its release notes opened with an instruction:

```
unihelm mail mta install
```

That was wrong twice.

**It was wrong as a design.** You run one installation command for this panel,
and after that whatever it needs happens from the panel. A release note that
opens with a chore is the product failing to do its job and asking the operator
to finish it by hand.

**And the command could not work.** Postfix's own postinst always writes an
`/etc/postfix/main.cf`, so the operation found a file it had not written on
every machine that had never had an MTA, and refused itself rather than take
over a configuration that might be somebody's real mail server. The documented
upgrade path failed on exactly the servers it was written for.

## What happens now

**Mail moves itself.** An upgraded server queues the migration the first time
the new agent starts; it appears in the task list as `mail.mta.install`, and
mail keeps working exactly as it did until the new path is verified against your
relay. Saving a relay in the panel does the same thing, so a server that has
never had mail set up needs one instruction rather than two.

`adopt` is decided by *when* `main.cf` appeared rather than whether it exists:
the panel may take over the file its own install just produced, and nothing
else. `unihelm mail mta install` remains for the one case that is genuinely a
person deciding — adopting a `main.cf` that was on the machine before Unihelm.

**Applications install their own runtime.** Creating an app whose runtime was
missing used to refuse with *"Install nodejs first, then create the app again"* —
sending the operator to a package manager for something the Stack Manager
installs. It installs it now, as a step in the task, and re-resolves the binary
afterwards: a package manager reporting success is not the same fact as a binary
being on the machine, and the panel will not write a unit pointing at nothing.

## Where the panel still says no, and why

The audit behind that change says no as often as yes, and the refusals now name
what *will* work instead of naming a command:

| Runtime | Debian / Ubuntu | RHEL family |
|---|---|---|
| Python, Ruby | installs | installs |
| Node | installs | **cannot** |
| Bun, Deno | **cannot** | **cannot** |

Node on the RHEL family cannot be installed because NodeSource lays its RPM
repositories out per distribution release in a way this panel cannot pin by
fingerprint, and Unihelm installs only from repositories pinned that way. Bun
and Deno are single vendor binaries with no signed repository at all. In every
one of those cases the refusal names the container that runs the app with
nothing installed on the host — a real answer rather than an errand.

Borrowing the Stack Manager borrows its permission: an account that may create
applications but may not install server software is told which Stack Manager
entry and version to ask an administrator for. Otherwise `node_apps` would
quietly have meant "may run the package manager as root".

---

Everything else in [0.8.0](0.8.0.md) is unchanged: 85 defects from a fresh-install
walkthrough, 23 more found by a pre-release review of those fixes, and mail
moving from a per-site PHP setting to a property of the machine.
